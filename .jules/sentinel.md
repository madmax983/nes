## 2024-05-22 - Infinite Loop on EOF in MCP Host
**Mutant:** Replaced `read == 0` with `read != 0` in `read_framed_message` inside `mcp_host.rs`.
**Diagnosis:** The test suite spawned the MCP Host which listens for TCP connections. When the test client dropped the connection, the host hit `EOF` (0 bytes read). Due to the mutation, the host thread entered an infinite loop. This hung `cargo test`, resulting in a `TIMEOUT` from `cargo-mutants`.
**Kill Shot:** In `cargo-mutants`, a mutant that causes a test suite timeout (e.g., an infinite loop on EOF) cannot be cleanly tracked as a "caught" mutant by default. To convert it into an explicit failure, wrap `std::io::Read` for the client `BufReader` with a struct (`PanicOnInfiniteEofReader`) that explicitly panics when it reads 0 bytes excessively. Apply this inside the tests that call `read_framed_message` and inside tests that spawn `TcpStream`s that might be impacted (by making sure the client reads will panic if the server drops connection due to the bug). Wait, this didn't resolve the timeout entirely when the server thread itself spins.
Actually, the client thread was the one spinning because tests like `mcp_host_slowloris` also call `read_framed_message` on the `TcpStream` from the client side, and the server dropping the connection meant the client got `EOF` and spun infinitely. Wrapping the client `TcpStream` in `PanicOnInfiniteEofReader` cleanly catches the mutant.
